# 本地推理提速：这轮到底改了什么

> 目标：**让「人设聊天」和「AI 对话」的首字和整段回答都更快**，并且给不愿意在本机跑模型的人
> 一条「用 OpenAI 格式 API 回答」的路。
>
> 所有改动都在两处：**提示词怎么排**、**谁来占用那把唯一的引擎锁**。
> 没有动模型权重、没有改采样质量。

---

## 一、先说结论：慢在哪

真机实测（HANDOFF §16.6）：同一条消息，**AI 对话 20.2 tok/s，人设聊天 2.8 tok/s**，
同一个模型、同一台机器。这个差距不是模型慢，是**提示词长**：

| | AI 对话 | 人设聊天 |
| --- | --- | --- |
| system prompt | 一句（约 30 字） | 人设 + 内在设定 + 关系状态 + 时间感 + 记忆 + 经验 + 疑问 + 表达能力（约 1500-3000 字） |
| 历史 | 24 条 | 24 条 |

而手机上 **prefill 比逐 token 生成还慢**。llama.cpp 的 KV cache 本来可以把「上一轮已经算过的
token」直接拿去用 —— 但它只认**从头开始逐字节相同**的那一段。

原来是这样的：

```
system = 人设 + 今天几号/几点 + 我们聊过 37 轮 + 你现在心情「有点低落」 + 我记得的 8 件事 + …
history = [system] + 最近 24 条消息
```

其中「聊过 37 轮」「心情」「记忆」**每轮都会变** → 公共前缀在 system prompt 中段就断了
→ 后面的历史、全部重算。**聊天越久越慢**，和模型本身没关系。

---

## 二、改法一：提示词分「稳定段 / 易变段」（最大的一处）

**稳定段**（跨轮不变）留在 system prompt：

  * 人设正文、内在设定、语气；
  * 能力声明（能不能发图 / 发表情 / 短话连发）；AI 对话的那一句系统提示词。

**易变段**（每轮都变）挂到**最新那条用户消息前面**，并且**存进那条消息**
（`ChatMessage.promptPrefix`，见 `data/Models.kt`）：

  * 关系状态（亲密度、心情、时间感、聊过几轮）；
  * 召回的 8 条记忆、经验、待问的疑问；
  * 设备感知（电量 / 位置 / 天气）；
  * 联网检索结果。

下一轮重建历史时**逐字节还原**那一段（`AppViewModel.send` 里的 `history` 构造），
于是「稳定段 + 全部历史」都落在可复用前缀里，每轮真正要算的只有一条新消息。

顺带四处细节，缺一个都会让复用失效：

1. **末尾那条空的 assistant 占位不算历史。** 它正好坐在「回答该出现的位置」上：
   留着它，上一轮生成的那几百个 token 永远落在缓存之外，每轮都要重算一遍。
2. **历史窗口按 6 条（3 轮）为步长滑动**（`historyWindow`）。普通的 `takeLast(24)`
   一旦超过 24 条就**每轮整体前移一条**，相邻两轮完全错位 —— 一次都命中不了。
3. **助手那一条用「原样生成」的文本**（`ChatMessage.rawContent`），不是界面上那份。
   界面那份被剔除过 `[[draw: …]]` / `[[emoji: …]]` 标记、被 trim、还会被短话连发
   切成好几条 —— 拿它重建历史，token 序列必然和上一轮真正进过缓存的不是同一串
   （实测：6 条短话的回复只命中了 19 个 token 就断开）。
4. **短话连发的后续分段不进提示词**（`ChatMessage.promptSkip`）。整轮回答由第一段
   的 `rawContent` 代表；否则同一段话在提示词里出现两次，而且在第一次出现处
   就已经和缓存对不上了。

同理，`CompanionPrompt` 也拆成了两半（见 `data/Companion.kt`）：

| 部分 | 内容 | 放哪 |
| --- | --- | --- |
| `buildStable` | 它是谁、关系到了哪一步、行为倾向、关系总结 | system prompt |
| `buildLive` | 聊过几轮、几点、此刻心情、召回了哪几条记忆、经验、待问的疑问 | 用户消息前缀 |

> 判断标准只有一条：**这东西多久变一次**。几天才变一次的放进稳定段（省下它每一轮的成本），
> 每轮都变的必须进易变段（它只花自己的长度，不会把整段历史一起拖下水）。
> ⚠️ 「经验」虽然变化慢，但**每轮学习都可能新增**，所以它留在易变段 —— 一旦进稳定段，
> 每新增一条经验就要把整段历史重算一遍。

---

## 三、改法二：学习不许排在用户前面（`LlamaEngine.Lane`）

手机上只有一个模型、一把锁。回答完之后程序还要「学」：提炼经验、每 12 轮重写关系总结 ——
这些都**要调模型**。原来的写法是在 `onTurnComplete` 里就地把整段跑完，
于是用户回完一句紧接着发下一句，那一句就排在提炼后面。真机反馈的
「回答完想接着说一句，半天没反应」就是这条路径。

现在：

  * `onTurnComplete` **立刻返回**，把活扔进 `LocalMindApp.learningScope`（后台 IO）；
  * 后台先等一个「没人等回答」的窗口：引擎空闲 **且** 用户没在输入框里打字
    （`LocalMindApp.userIsTyping`，由 `setDraft` 维护）；
  * 学习任务里的模型调用走 `LlamaEngine.Lane.BACKGROUND`：
    - 开工前发现前台有请求 → **这一次直接放弃**（宁可丢一条记忆）；
    - 已经跑起来了、用户又发了消息 → 前台**直接掐掉**后台那轮（`nativeCancel`）。

---

## 四、改法三：三段准备工作并行

「按含义召回记忆」「读设备感知」「联网检索」互不依赖，原来是一条条 `await` 的。
串行时首 token 要等三者相加（定位冷启动能到 2-4 秒），现在 `async` 并行，只等最慢的那一个。

---

## 五、改法四：写盘不再占着主线程

`persistConversations()` 原来是**同步**把「全部对话 + 每条消息」序列化成一个 JSON 再写文件，
而发送一条消息要跑两遍，全在主线程上。聊天记录越长越慢，最坏情况正好卡在
「点了发送、等第一个字出来」的那几百毫秒里。

现在：浅快照（只复制引用）+ IO 线程 + 250 ms 合并。新建 / 删除 / 清空这类结构性改动
仍然立即写（`delayMs = 0`）。

---

## 六、改法五：OpenAI 格式 API 直接进对话设置

「AI 对话设置」和「人设聊天设置」里都多了一块 **用 API 回答（OpenAI 格式）**：

  * 一键切换：本机 / 任意已启用的接口（写入 `conversation.chatModelId`）；
  * 现场新建：名称 / Base URL / API Key / 模型名 → 点一次就**接入 + 绑定这个对话 + 探活**；
  * 也会自动补 `/v1`（只对路径为空的地址补；像智谱 `/api/paas/v4`、Gemini `/v1beta`
    这种多补一层就是 404，所以刻意不碰）。

⚠️ 走 API 时**记忆、情绪、经验照常工作** —— 那些是程序算的，和谁在说话无关。

### 实测（模拟器 + `tools/mock-upstream.js` 假上游）

把人设聊天的 `chatModelId` 指向一个本地假上游（`http://10.0.2.2:9099/v1`）之后：

```
>>> POST /v1/chat/completions
    auth= Bearer sk-test
    body= {"model":"mock-chat","stream":true,"messages":[{"role":"system","content":"【你自己的设定】…"}]}
```

界面上气泡是 `MOCK-OPENAI:mock-chat`，**整轮约 1 秒**（同一个对话走本机 0.5B 时，
这个模拟器要几分钟）。也就是说：「想立刻变快」这件事，接 API 是**目前最有效的一招**，
而它现在就在对话设置里。

## 七、怎么验证（不用信，直接看数字）

原生侧每一轮都往 logcat 打一行：

```
LocalMindNative: prefill: prompt=2431 reused=2278 (94%) new=153 in 412ms
LocalMindNative: generate: 88 tokens in 5210ms (16.9 t/s)
```

  * `reused` 就是**这一轮直接复用 KV cache、没有重算**的 token 数；
  * `new` 才是真正要算的（正常情况下就是「你刚发的那句话 + 易变段」）。

Kotlin 侧同时把那三个数字写进 `EngineState`：

| 字段 | 含义 |
| --- | --- |
| `lastPromptTokens` / `lastReusedTokens` / `cacheHitPercent` | 提示词多大比例是从缓存读的 |
| `lastPrefillMs` | prefill 墙钟时间（≈ 首 token 之前的那段等待） |
| `lastFirstTokenMs` | 从点发送到第一个字出来 |
| `lastGenMs` | 逐 token 生成用了多久 |

界面上的位置：

  * 生成过程中输入框上方那行小字：`88 tokens · 16.9 tok/s · 缓存命中 94%`；
  * 走 API 时那行改成 `API 直连 · 推理在云端，本机不加载模型`；
  * 测试模式 / 诊断报告里有一行「前缀复用」与「prefill」。

```bash
adb logcat -s LocalMindNative:* LlamaEngine:*
```

> **判据**：人设聊天连发三句，第二、三句的 `reused` 应当占到 prompt 的 80% 以上。
> 如果 `reused` 一直在个位数 —— 说明又有东西被塞进稳定段了（或「易变段」被改写），
> 那就是回归，不是模型的问题。

### 本轮实测（Android 15 / x86_64 模拟器 / Qwen2.5 0.5B Q4_K_M，人设聊天）

| 轮次 | prompt | reused | new | prefill |
| --- | --- | --- | --- | --- |
| 1 | 700 | 0 (0%) | 700 | 90 013 ms |
| 2 | 1051 | **719 (68%)** | 332 | 46 308 ms |

第 2 轮的 332 个「新」token 里，绝大部分是**上一轮那 6 条短话回复**（改之前它们必然要重算）
加上易变段。68% 这个数字说明稳定段已经命中了；把 `rawContent` / `promptSkip` 补上之后，
上一轮的回复也会落进可复用前缀，理论新增降到「易变段 + 这一句话」≈ 250-300 token。

> 模拟器上的**墙钟时间不能当真**：first prefill 要把 468 MB 权重从虚拟磁盘读进来（约 8 tok/s），
> 换台真机同一段 prompt 是零点几秒到两秒。这里只比 `reused / prompt` —— 那才是布局改对没改对的判据。

## 八、这一轮**没有**动的东西（以及为什么）

| 想动的 | 为什么不动 |
| --- | --- |
| 砍人设 / 砍记忆来提速 | HANDOFF §16.6 已经定过调子：人设那几千字是**功能本身**，不是浪费。要快应该去修布局，不是删内容。 |
| 投机解码（draft model） | 需要第二个模型常驻内存，手机上代价太大；收益也不稳定。 |
| 更大的 `n_batch` / 更多线程 | 已经在设置里（512 / 256 / 4 线程）。真机大核数判断没有可靠的公开 API，猜错反而更慢。 |
| 关掉 flash attention | 有实测报告说 Arm 上有负收益 —— 所以它是**可关的开关**（默认 AUTO），而不是写死的结论。 |

## 十、1.0.3 追加：又抠出来的四处（同样的模型，更快一点）

| # | 改了什么 | 之前 | 之后 | 为什么快 |
| --- | --- | --- | --- | --- |
| 1 | **prefill 的线程数**（`n_threads_batch`） | 和生成一样（4） | `min(核数, 6)`，但不少于生成线程 | 逐 token 生成卡内存带宽，多线程没用；**prefill 是算力活**，几千 token 的提示词全靠它 |
| 2 | **KV cache 精度** | f16（默认） | **q8_0** | 注意力阶段按字节从 KV 里读，q8 少读一半；顺带上下文从 3584 涨到 7168 |
| 3 | **prefill 逻辑批** | 512 | **1024** | 少切几次图（每次切图都要重建计算图）。占内存的是 ubatch，所以几乎不涨内存 |
| 4 | **生图线程数** | `autoThreads()` = 4 | `max(4, min(核数, 6))` | 扩散 UNet 是算力活，4 线程在 8 核机上空转一半的核 |

### 老用户怎么拿到（这很关键）

`GenerationSettings` 的默认值**只在第一次写盘之前**生效。老用户手机里存着
`kvQuant=f16` / `batchSize=512` 这两个旧默认值，所以只改 Kotlin 的 `default` 对他们
**零作用**。为此加了一次性迁移（`Storage.KEY_GEN_V2`）：
**精确匹配旧默认值才迁**，用户自己调过的值一律不碰。

同理生图尺寸的 768²→512² 也是同样的做法（`KEY_IMAGE_SIZE_V2`）。

### 实测（模拟器，4 核，所以第 1 项在模拟器上等于没变）

```
改之前：kv=f16  · n_batch=512  · 上下文 3584
改之后：kv=q8_0 · n_batch=1024 · 上下文 7168   ← 同样 1.5GB 内存预算，上下文翻倍
```

> 真机（8 核）上第 1 项才会体现：`threads=4/6`（生成 4、prefill 6）。
> 诊断页的「加速配置」那一行现在直接显示 `threads=4/6`，可自行核对。
| 5 | **模型预热** | 首次生成的缺页发生在「正在思考」里 | 加载阶段用 1 MB 缓冲**顺序读一遍**权重（界面本来就在「正在加载」）。只在模型装得进内存时做 —— 装不下时顺序读会把热的页挤掉，反而更慢 |

### 实测（模拟器 / 1.5 GB 内存 / Qwen2.5 0.5B）

```
加载：预热完成 1860 ms（468 MB 顺序读）
第 1 条消息：prompt=51  prefill=11338 ms
第 2 条消息：prompt=69  reused=58 (84%)  prefill=6671 ms
```

> ⚠️ 这组数字只能看**相对关系**，不能当真机参考：模拟器只有 1.5 GB 内存，
> 468 MB 的权重在两次生成之间会被内核挤出页缓存，于是每次都要重新缺页 ——
> 这就是「69 个 token 也要 6.7 秒」的全部原因（计算量可以忽略）。
> 真机（8 GB 以上）不会这样，预热的收益在那时才是真实的。

> 第 1 条 vs 第 2 条的 11.3 s → 6.7 s 里，58/69 是**前缀复用**命中（84%），
> 说明提示词布局那套在真实链路上确实生效。
