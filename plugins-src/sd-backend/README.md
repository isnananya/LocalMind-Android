# 本地生图后端（通用版） · LocalMind 插件

装上之后，LocalMind 才能用 **Stable Diffusion 系列模型**真正生成图片。

这一版是**通用版**：一个 zip 同时带 **arm64-v8a（手机）** 和 **x86_64（模拟器 / Intel 设备）**，
安装时按本机 ABI 自动选一份；同一份 JNI 还多给了四类参数：

| 能力 | 说明 |
| --- | --- |
| 采样步数 | 1–N 步；0 = 用 checkpoint 自己的默认值 |
| 线程数 / flash attention | 建上下文时生效，改设置后会自动重建 |
| 采样器 / 调度器 | euler_a / lcm / dpm++2m …；空串 = 交给 sd.cpp 按模型族决定 |
| 逐帧进度 | 生成过程中回报「第几步 / 共几步」，界面不再是干转圈 |

> 通用版通过新的 JNI 入口 nativeSdGenerateEx2 提供；旧 APK 或旧插件仍能出图，
> 只是拿不到采样器和进度。主程序会按「Ex2 → Ex → 基础入口」三级回退。

## 为什么它是单独的插件

主程序不带这个后端。理由有两个，都不是“懒得内置”：

**1. 体积**。后端 strip 后约 37 MB/ABI，而它只有**愿意再下 1.5–6 GB 模型**的人
才用得上。打进安装包意味着每个用户都为它付这份体积 —— 包括那些只用对话和语音的人。
按需下载之后，不用生图的人一分钱不付。

**2. ABI 冲突**。这个后端用 [stable-diffusion.cpp](https://github.com/leejet/stable-diffusion.cpp)，
它自带一份 ggml；对话用的 llama.cpp 也自带一份。两份 ggml 的
GGML_MAX_NAME 不一样（160 vs 64），而 char name[GGML_MAX_NAME] 是
struct ggml_tensor 里的**真实字段** —— 于是两边眼里的 sizeof(ggml_tensor)
差 96 字节，extra / view_src 落在不同偏移上。

**这不会报链接错误**，只是运行时的内存错乱。把两者放进同一个 .so
只能靠“全局统一宏”来绕，代价是 llama 跑在 sd.cpp 那位打过补丁的 ggml 上 ——
任一方升级 ggml，这个巧合就没了，而且不会有任何编译期提示。

分成两个 .so 之后，Android 的链接器在解析符号时**先看库自己**，
两个 ggml 各自留在自己的库里，冲突从结构上消失。

## 装完之后还要什么

**还需要一个模型**。后端只是推理引擎，不含权重 —— 像装了个播放器但没有影片。

去 **模型 → 生图** 分类下载一个 .gguf，或者把你已有的放进
应用目录的 files/models/。支持 SD1.5 / SDXL / SD-Turbo / LCM / Flux 等
stable-diffusion.cpp 能读的格式。

建议从 **SD-Turbo**、**LCM** 或 **SDXS** 开始：它们 1–4 步就能出图，
手机 CPU 上几十秒；标准 SD1.5 默认 12 步，会慢一些。

## 不装会怎样

不装也能生图，用的是主程序自带的**程序化渲染器**：不下载任何东西、
立刻可用、完全离线、同一提示词 + 同一随机种子必定得到同一张图。

它画不出提示词里的具体内容（那不是扩散模型在做的事），但出来的是一张
真正能用的图，而不是一块灰色占位。

装了后端但**没有模型**时，行为和不装一样 —— 自动退回程序化渲染。

## 技术细节

- **ABI**：包内 lib/arm64-v8a/ 与 lib/x86_64/ 各一份，安装器只解压本机
  那一种；32 位设备（armeabi-v7a）**不在支持范围内**：扩散推理在 32 位地址
  空间里跑不动几 GB 的模型。
- **依赖**：liblog / libm / libdl / libc++_shared / libc —— 都是系统库，
  随 Android 提供，不需要额外安装。
- **加载**：安装后落到 filesDir/native/<abi>/liblocalmind-sd.so，由
  System.load 加载。加载失败不会让应用崩溃，只会退回程序化渲染。
- **线程**：默认用满 CPU 核心数（上限 6）。手机上生图会明显发热，这是正常的。
